## 1. Proposed scope (what the helper would be)

An `SMAppService` daemon (launchd-managed, no root login shape) exposing a
minimal, versioned IPC surface to AppUpdater itself:

- Install operator-approved **PKG** payloads (`installer -pkg`) for the app
  classes our user-space installer refuses today (PKG-distribution updates).
- Nothing else. No scheduled background installs, no network access, no
  file дешев management beyond its own install staging area.

Why it exists at all: today the CLI honestly refuses `install --apply` when the
only artifact is a PKG (Phase 3 documented boundary). The helper is what makes
that refusal optional instead of permanent — IF the owner wants the risk surface.

## 2. Assets in scope

| Asset | Exposure if compromised |
|---|---|
| Helper's execution privilege (root) | Arbitrary code execution as root on this machine |
| The IPC protocol between app/CLI and helper | Command forgery → drive-by root installs |
| Downgrade/executable path of the helper itself | Running an OLD known-buggy version (revive-kill) |
| PKG payload staging dir | Payload swap between verification and installation (TOCTOU) |
| The owner's consent gesture ("apply this PKG") | Silent widening from one consented install to a standing policy |

## 3. Threat vectors + required mitigations (each mitigation is a gate line, not a wish)

1. **IPC forgery / unauthorized caller.** The helper verifies the caller's
   code signature against a pinned requirement string (TeamID/designators of
   the AppUpdater app bundle only) before serving any request. Non-matching
   callers get refused with a receipt; nothing executes.
2. **TOCTOU payload swap.** The helper verifies the PKG itself (checksum from
   the receipt + `pkgutil --check-signature` result carried in the request)
   AFTER staging and IMMEDIATELY before `installer` invocation, in the same
   task; staging dir is per-apply UUID, mode 0700, removed on every outcome.
3. **Consent widening.** The helper has NO standing rules table. Every install
   requires a fresh, explicit, per-apply IPC call that includes the app name +
   version + checksum, and the helper REJECTS any request lacking all three.
   Auto-apply remains nonexistent by design (LOCKED product boundary).
4. **Helper downgrade / revive-kill.** launchd entry pins the code requirement;
   the app verifies the helper's version + signature on first contact and
   refuses to speak to an unversioned or unsigned helper (case: attacker
   replaces the binary with an old copy — version handshake beats file path).
5. **Prompt injection via update metadata.** All strings surfaced to the helper
   (app name, path, version, checksum) are generated by AppUpdater from the
   verified receipt chain (Phase 3 coordinator), never read from the cask /
   appcast JSON payload verbatim — payload-authored names can never become
   arguments. This rule is enforced by construction (helper takes the
   checksum + bundle ID, never free text).
6. **Rollback safety.** `installer` has no rollback: the helper requires the
   written backup receipt (zip) the user-space installer already produces and
   refuses to run without it, so every root install remains reversible the
   same way Phase 3 applies are.
7. **No network, no telemetry** inside the helper (enforced by review: zero
   URLSession symbols; lint/CI grep gate after implementation).
8. **Auditability.** Every helper action appends to a local receipt log owned
   by the helper (who asked, what, when, checksum, result); receipt content is
   what the owner sees in the CLI `install` output.

## 4. Residual risks accepted even after mitigations (say them out loud)

- A compromised helper IS root. The mitigations reduce the blast surface; they
  do not make root smaller.
- SMAppService registration requires developer-signed signed binaries; on the
  current personal-use signing (no Developer ID), the correct answer is
  **do not ship the helper at all** until Developer ID exists — this is a hard
  ordering dependency on the Apple Developer enrollment open item.
- `installer` behavior varies across macOS releases; PKG validation semantics
  (`pkgutil --check-signature`) trust the certificate chain present on THIS
  machine, which is the exact scope of trust we are declaring.
